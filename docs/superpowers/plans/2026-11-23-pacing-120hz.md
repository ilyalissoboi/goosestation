# Frame pacing at 120 Hz (Android) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a 120 Hz Android screen, each NTSC frame is shown for exactly two refreshes in at least 95% of seconds
(the AYN Thor's own screen), with 60 Hz unchanged.

**Architecture:** Two changes to stage 2a's screen lock. (1) The lock accepts a screen within 2% of a whole multiple of
the console's rate, not 0.5%: the Thor's "120 Hz" panel really runs at 118.36 Hz, so the lock never engaged there.
(2) When each frame takes two or more refreshes, its present asks not to be shown before half a refresh ahead of the
timeline refresh it was planned for (`VK_GOOGLE_display_timing`'s `desiredPresentTime`,
`eglPresentationTimeANDROID`). Then a frame that is ready early waits for its refresh instead of taking the one
before. The time comes from the Choreographer timeline the frame was planned on, never from counting frames shown.

**Tech Stack:** C++20 core (`src/core`), `src/util` GPU devices (Vulkan, EGL), gtest (`src/common-tests`), the Android
instrumented tiers, the Thor harness (outside the repo).

**Spec:** `docs/superpowers/specs/2026-11-20-gpu-thread-and-pacing-design.md`, "Stage 2, revised (2026-11-22)" ("at
120 Hz, each NTSC frame shown for two refreshes"). The measurements behind this plan are in the shared notes folder,
`pacing-120hz-findings.md`.

## What the spike found (2026-11-23, Thor, Vulkan unless said)

- The panel runs at 8.449 ms at "120 Hz" (118.36 Hz) and 16.731 ms at "60 Hz" (59.77 Hz), from SurfaceFlinger's own
  present times. Choreographer's ticks agree.
- Two refreshes a frame need the game at 59.18 Hz, 1.07% below NTSC: outside `RefreshesPerFrame`'s 0.5%. So #140 never
  locked at 120 Hz on the Thor. Its 120 Hz figures were the plain sync-to-host throttle.
- #140's 67–68% used the 60 Hz test (slowest frame ≤ 17.5 ms), which can't see a frame shown early. Counted as "every
  frame exactly two refreshes", #140 at 120 Hz is 0% of seconds.
- Lock window 2%, lock alone: 5–7% of seconds even (frames shown a refresh early).
- Lock window 2% plus the desired present: Vulkan 92% (60 s) and 96% (120 s); OpenGL ES 97%; lag 5.6–10 ms.
- The same desired present at 60 Hz made things worse: 93% even and lag 28.1 ms, against 97% and 23.3 ms without it.
  So it applies at two refreshes a frame and more only.
- B (`ASurfaceControl` with frame-timeline IDs) isn't needed for the target and is not part of this plan.

## Review Focus

1. A screen 2% off a multiple now locks, so the game runs up to 2% slow or fast. The audio must follow the locked speed
   as it does at 60 Hz (the sync-to-host resampler), with no drift or crackle at 118.36 Hz.
2. A 60 ↔ 120 Hz switch mid-game: a frame planned at 120 must not carry a desired present into a 60 Hz lock, holding it
   a refresh. Desired presents go with the refreshes per frame of the plan the frame was made on.
3. Unlocking (pause, fast-forward, menu): presents after it carry no desired present time (0), so the UI is never held.
4. Vulkan's present thread (GPU thread off, threaded presentation): no desired present time there, because feedback is
   off in that configuration (as #140 does for present IDs).
5. A desired present time in the past (a frame that ran long) shows the frame at once, never later.

### Task 2: A frame on two refreshes isn't shown before its refresh

**Files:**
- Modify:
  - `src/core/frame_pacing.{h,cpp}` (`Wake` and `NextWake`; a new `DesiredPresent`);
  - `src/core/system.cpp` (`SleepToDisplayDeadline`, the locked present in `FrameDone`, `PresentDisplay`);
  - `src/core/gpu_thread_commands.{h,cpp}` (the command's field, `HandlePresent`);
  - `src/util/gpu_device.h` (`SetNextPresentTime`);
  - `src/util/vulkan_device.{h,cpp}` and `src/util/opengl_device.{h,cpp}`;
  - `src/util/opengl_context.h` and `src/util/opengl_context_egl.{h,cpp}`.
- Test: `src/common-tests/frame_pacing_tests.cpp`

**Interfaces:**
- Produces:
  - `struct Wake { wake_time; deadline; Common::Timer::Value refresh; }`: `refresh` is the timeline's expected present
    of the refresh the deadline belongs to (`deadline + timeline.deadline_lead`, using the `deadline_lead` passed in,
    which is the aimed one); 0 without a timeline.
  - `Common::Timer::Value FramePacing::DesiredPresent(Common::Timer::Value refresh, Common::Timer::Value period, u32 refreshes_per_frame)`:
    `refresh - period / 2` when `refreshes_per_frame >= 2` and `refresh != 0`; else 0 (no request).
  - `virtual void GPUDevice::SetNextPresentTime(u64 time)`: the earliest the next present may be shown
    (Common::Timer's clock, 0 for none). It holds for the next present only. A no-op by default. Vulkan sets it only
    where `HasPresentFeedback()`, as `VkPresentTimeGOOGLE::desiredPresentTime`. OpenGL ES sets it only with
    `EGL_ANDROID_presentation_time` and frame timestamps on, through `eglPresentationTimeANDROID` before the swap.
  - `GPUThreadPresentCommand::desired_present` (Common::Timer::Value, 0 for none), a new last parameter of
    `GPUThreadCommands::PushPresent` (default 0). `HandlePresent` calls `SetNextPresentTime(cmd->desired_present)`
    before presenting, and only when it is non-zero.
